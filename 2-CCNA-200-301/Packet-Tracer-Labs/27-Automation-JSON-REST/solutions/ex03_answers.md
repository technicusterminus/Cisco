# Antworten Aufgabe 3

1. **Inventory = die Zielgeräte, Playbook = die Datei, Play = Hosts plus Tasks, Task = ein Modulaufruf, Modul = der Code dahinter, Handler = Task auf Abruf, Variable = Parameter.** Im Playbook ist alles ab `- name: Switch-Basiskonfiguration` ein Play, jeder Eintrag unter `tasks` ein Task, `cisco.ios.ios_config` das Modul und `speichern` der Handler, den `notify` aufruft. Variablen schreibst du als `{{ var }}`, das Inventory liegt in einer eigenen Datei.
2. **Ansible braucht auf dem Zielgerät keine Software.** Es verbindet sich vom Kontrollknoten per SSH, NETCONF oder API und schiebt die Änderung (Push). Puppet und Chef brauchen einen Agenten, der den Sollzustand beim Server abholt (Pull). Auf Netzwerkgeräten läuft meist kein Agent, deshalb passt agentenlos.
3. **Idempotent heißt: Ein zweiter Lauf ändert nichts mehr.** `ios_config` vergleicht `lines` mit der laufenden Konfiguration und sendet nur, was fehlt. Beim zweiten Lauf meldet Ansible deshalb `ok` statt `changed`.
4. **Sieben Fehler.** `hosts` fehlt, `gather_facts` steht auf `true`, `connection: local` statt `ansible.netcommon.network_cli`, das Modul `ios_config` ist nicht voll qualifiziert, im ersten Task sind `lines` und `parents` vertauscht (und keine Listen), im zweiten ist `parents` keine Liste, und der Handler `speichern` fehlt. Die Lösung steht in `solutions/ex03_playbook_fixed.yml`.
5. **Deklarativ beschreibst du das Ziel, imperativ die Schritte.** Bei Terraform schreibst du „es gibt ein VPC mit diesem Netz“, das Werkzeug berechnet selbst, was zu tun ist. Ein Skript sagt dagegen Schritt für Schritt, was passieren soll.
6. **`provider` verbindet zur Plattform, `resource` ist ein verwaltetes Objekt, `variable` eine Eingabe, `output` ein Ergebnis.** In `main.tf` ist der Provider AWS, die Ressourcen sind ein VPC und ein Subnetz, `region` ist die Variable und `vpc_id` die Ausgabe.
7. **`init` lädt die Provider, `plan` zeigt die Änderungen, `apply` führt sie aus, `destroy` baut alles ab.** Die State-Datei merkt sich, welche reale Ressource zu welchem Objekt im Code gehört. Nur so kann `plan` Ist und Soll vergleichen.
8. **Infrastruktur wird wie Software behandelt.** Der Code liegt in Git, also mit Historie. Änderungen laufen durch ein Review, und dieselbe Umgebung lässt sich jederzeit identisch neu aufbauen.
9. **Terraform baut die Infrastruktur, Ansible konfiguriert sie.** Terraform verwaltet den Lebenszyklus von Ressourcen, besonders in der Cloud, und führt dafür einen State. Ansible richtet vorhandene Geräte und Server ein und braucht keinen State. Oft arbeiten beide zusammen.
