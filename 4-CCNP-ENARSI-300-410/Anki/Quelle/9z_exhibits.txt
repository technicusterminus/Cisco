# 1.6 | Policy-Based Routing
S: https://www.cisco.com/c/en/us/support/docs/ip/ip-routed-protocols/48003-pbrtracking.html | Cisco: PBR with Next-Hop Tracking

Q: Verkehr aus 10.1.1.0/24 kommt auf Gi0/0 herein und soll über den Next Hop 10.0.23.3 gehen. Die Route-Map zählt aber nichts.
```
R1# show route-map PBR
route-map PBR, permit, sequence 10
  Match clauses:
    ip address (access-lists): 101
```

# 1.9.b | EIGRP: Nachbarschaft und Authentisierung
S: https://www.rfc-editor.org/rfc/rfc7868 | RFC 7868: Cisco's Enhanced Interior Gateway Routing Protocol

Q: R1 und R2 sind direkt verbunden und beide laufen im AS 100, die Nachbarschaft kommt aber nie zustande. Im Log steht diese Meldung.
```
%DUAL-5-NBRCHANGE: EIGRP-IPv4 100: Neighbor 10.0.12.2 (GigabitEthernet0/0) is down: K-value mismatch
```
Was ist die Ursache?
A: **Die K-Werte (metric weights) unterscheiden sich auf beiden Seiten.** EIGRP-Nachbarn müssen dieselben K-Werte verwenden, sonst bauen sie keine Nachbarschaft auf. `show ip protocols` zeigt die K-Werte. Standard ist K1=K3=1 und K2=K4=K5=0, nach einem `metric weights` stehen sie anders.

# 1.9.c | EIGRP: Loop-freie Pfadwahl
S: https://www.rfc-editor.org/rfc/rfc7868 | RFC 7868: Cisco's Enhanced Interior Gateway Routing Protocol

Q: In `show ip eigrp topology` steht vor der Route 10.9.0.0/16 der Code „A“ statt „P“, und das bleibt über Minuten so. Was bedeutet das?
A: **Die Route ist Active: Der Router hat keinen Feasible Successor mehr und wartet auf Replies seiner Nachbarn.** Kommt eine Antwort nicht rechtzeitig (Active Timer, standardmäßig 3 Minuten), wird die Route „stuck in active“ und die Nachbarschaft zurückgesetzt. Abhilfe: Queries mit Stub-Routern und Summarization eingrenzen.

# 1.9.d | EIGRP: Stub
S: https://www.rfc-editor.org/rfc/rfc7868 | RFC 7868: Cisco's Enhanced Interior Gateway Routing Protocol

```
Hub# show ip eigrp neighbors detail
H   Address         Interface    Hold Uptime   SRTT   RTO  Q  Seq
```

# 1.10.b | OSPF: Nachbarschaft und Authentisierung
S: https://www.rfc-editor.org/rfc/rfc2328 | RFC 2328: OSPF Version 2

Q: Zwei OSPF-Router hängen dauerhaft im Zustand EXSTART und wechseln immer wieder.
```
R1# show ip ospf neighbor
Neighbor ID     Pri   State           Dead Time   Address         Interface
2.2.2.2           1   EXSTART/DR      00:00:36    10.0.12.2       GigabitEthernet0/0
```
Was prüfst du zuerst?
A: **Die MTU der beiden Interfaces.** In EXSTART/EXCHANGE tauschen die Router Datenbankbeschreibungen aus. Stimmt die Interface-MTU nicht überein, werden diese Pakete verworfen und der Zustand wechselt. Die saubere Lösung ist dieselbe MTU auf beiden Seiten, notfalls hilft `ip ospf mtu-ignore`.
T: Exhibit Mittel

Q: In `debug ip ospf hello` erscheint diese Meldung.
```
OSPF-1 HELLO Gi0/0: Rcv hello from 2.2.2.2 area 0 10.0.12.2
OSPF-1 HELLO Gi0/0: Mismatched hello parameters from 10.0.12.2
OSPF-1 HELLO Gi0/0: Dead R 40 C 120, Hello R 10 C 30
```
Was ist unterschiedlich, und welche Seite hat welchen Wert?
A: **Hello- und Dead-Intervall unterscheiden sich: R steht für „received“, also vom Nachbarn (Hello 10, Dead 40), C für „configured“, also lokal (Hello 30, Dead 120).** Hello- und Dead-Intervall müssen auf beiden Seiten gleich sein, sonst gibt es keine Nachbarschaft.

Q: Auf einem Broadcast-Segment zeigt R1 zu R3 den Zustand 2WAY/DROTHER.

```
Neighbor ID     Pri   State           Dead Time   Address         Interface
3.3.3.3           1   2WAY/DROTHER    00:00:33    10.0.0.3        GigabitEthernet0/0
4.4.4.4           1   FULL/DR         00:00:31    10.0.0.4        GigabitEthernet0/0
5.5.5.5           1   FULL/BDR        00:00:38    10.0.0.5        GigabitEthernet0/0
```
Ist das ein Fehler?
A: **Nein, das ist normal.** Auf Broadcast-Segmenten gehen nur DR und BDR eine volle Adjazenz mit allen anderen ein. Zwei DROther-Router bleiben in 2WAY und tauschen ihre Datenbanken über den DR aus.

# 1.10.c | OSPF: Virtual Links
S: https://www.rfc-editor.org/rfc/rfc2328 | RFC 2328: OSPF Version 2

Q: Der Virtual Link zwischen zwei ABRs kommt nicht hoch.
```
R1# show ip ospf virtual-links
Virtual Link OSPF_VL0 to router 3.3.3.3 is down
  Transit area 1, via interface GigabitEthernet0/1
```

Welche Ursachen kommen nach dieser Ausgabe in Frage?

# 1.11.c | BGP: Pfadwahl

```

BGP routing table entry for 10.9.0.0/16, version 12
Paths: (2 available, best #1, table default)
  Refresh Epoch 1
  65002 65010 65020
    10.0.12.2 from 10.0.12.2 (2.2.2.2)
      Origin IGP, metric 0, localpref 200, valid, external, best
  Refresh Epoch 1
  65003
```

# 3.2.a | IPv4-ACLs: Fehlersuche
S: https://www.cisco.com/c/en/us/support/docs/security/ios-firewall/23602-confaccesslists.html | Cisco: Configure and Filter IP Access Lists

Q: Du siehst diesen Ausschnitt.
```
R1# show ip access-lists OUT-FILTER
Extended IP access list OUT-FILTER
    10 permit tcp 10.1.1.0 0.0.0.255 any eq www (1234 matches)
```

# 3.2.b | IPv6 Traffic Filter
S: https://www.rfc-editor.org/rfc/rfc4861 | RFC 4861: Neighbor Discovery for IPv6

Q: Nach dem Anlegen dieser ACL am Interface fällt IPv6 komplett aus, auch die Adressauflösung.
```
ipv6 access-list BLOCK-ALL
 permit tcp any any eq 22
 deny ipv6 any any log
interface GigabitEthernet0/0
 ipv6 traffic-filter BLOCK-ALL in
```
Warum?
A: **Das explizite `deny ipv6 any any` überschreibt die impliziten Regeln für Neighbor Discovery.** Eine IPv6-ACL enthält am Ende unsichtbar `permit icmp any any nd-na`, `permit icmp any any nd-ns` und danach `deny ipv6 any any`. Steht ein eigenes Deny davor, greifen die ND-Permits nie. Füge `permit icmp any any nd-ns` und `nd-na` vor dem Deny ein.

# 3.2.c | uRPF: Fehlersuche
